# Service API

## What is this repository?

This repository contains an implementation of the Service API module proposed in the IEEE Internet Computing paper "Active Inference for Sustainable Computing Continuum Systems". For now, it implements an API for the media server Jellyfin, which fulfills one of the use cases stated in the paper. The service API offers control over the configuration parameters of the service, as well as observability of declared SLOs.

The API is implemented using as a baseline an OpenAPI-generated Python Flask server.

## What do I need to run this?

You need Python 3.5.2+ to run the API in a bare-metal system, as well as `pip` to install the requirements. Alternatively, you can use the Docker version, for which, you will need a container runtime (e.g. `docker`).

## Repository structure

- `.openapi-generator`: Metadata from the OpenAPI generator.
- `media_server_api`: Code for the API, part of which was generated by OpenAPI generator. Individual files are subject to changes. Those auto-generated are not explained.
    - `api_controllers`: Controllers for the APIs. The API logic is here.
    - `models`: Python models for the OpenAPI definitions.
    - `openapi`: Copy of the API definition used by the server.
    - `service_controller`: Implementation of the part of the API that controls services.
        - `__init__.py`: Declares the `ServiceController` abstract base class, which must be extended to implement specific service controllers, and `ControlException` for uncontrolled runtime exceptions during service control.
        - `jellyfin`: Implementation of a service controller for Jellyfin.
            - `config.py`: Jellyfin-specific configuration variables.
            - `jellyfin.py`: Implementation of the `JellyfinController` class.
    - `slo_controller`: Implementation of the SLO observability part of the API.
        - `__init__.py`: Includes the abstract base class `SLOController`, which must be extended to implement SLO controllers, and the specific implementation for InfluxDB as an `InfluxDBSLOController`.
        - `config.py`: SLO-specific configuration variables.
        - `parser.py`: Declares the abstract base class `SLOParser`, for parsing SLO configurations from multiple formats, and the specific implementation for JSON (`JSONSLOParser`).
    - `test`: Tests of the API. As of now, not implemented.
    - `__main__.py`: Main file that executes the application, with the necessary workarounds to use Gunicorn adequately. `api_bridge` objects should be populated here.
    - `api_bridge.py`: As the OpenAPI-generated server is not very friendly to dependency injection, this module keeps objects it must access (e.g. SLO and service controllers).
    - `config.py`: Configuration variables for the API.
- `.dockerignore`: Files that should be ignored during a Docker build.
- `.openapi-generator-ignore`: Files to be ignored by the OpenAPI generator.
- `.travis.yml`: Configuration for Travis CI. As of now unused.
- `Dockerfile`: Dockerfile for building a Docker image.
- `git_push.sh`: Script for applying git-flow. Unused.
- `README.md`: This file.
- `requirements.txt`: Requirements for the API.
- `setup.py`: Setup to install this API as a Python package.
- `test-requirements.txt`: Requirements for testing the API.
- `tox.ini`: Tox configuration.

## Setup details (for replicability)

No setup is required, refer to the Instructions section for execution instructions.

### Tools and data used

- Tool used to generate the basis of the service API: `openapi-generator` 7.14.0-1 ([Arch Linux package](https://archlinux.org/packages/extra/any/openapi-generator/))
- Tool used to containerize: `docker` 1:28.3.3-1 ([Arch Linux package](https://archlinux.org/packages/extra/x86_64/docker/))
- Tool used to manage the container deployment: `docker-compose` 2.39.2-1 ([Arch Linux package](https://archlinux.org/packages/extra/x86_64/docker-compose/))

### Instructions

#### Bare-metal

1. (Recommended, but optional): Create and activate a Python virtual environment: `python3 -m venv .venv`, `. .venv/bin/activate`.
2. Install the requirements. `pip3 install -r requirements.txt`.
3. Run the API as a module: `python3 -m media_server_api`.
5. The EMMA API will be available at `http://localhost:80/v0`, with docs and a UI at `http://localhost:80/v0/ui`.

#### Docker (recommended)

Refer to the higher-level Docker-Compose configuration.

#### (Optional) re-generation of server code

The codebase for this project was generated using the `openapi-generator` tool. To re-generate this initial code, you can use the `batch-openapi-generator.yaml` configuration. Use the command `openapi-generator-cli batch batch-openapi-generator.yaml` to do so. **We, however, do not recommend doing this unless you have a very good reason to do so**, as the generator may break many parts of the sytem.

## SLO configuration

SLO configurations allow the API to know which SLOs to show to the outside and how to get them. As of now, this is done with a JSON configuration that queries InfluxDB.

### InfluxDB-JSON SLO configuration format

```json
[
    {
        "id": "<ID-OF-THE-SLO>",
        "name": "<LONG-NAME-OR-DESCRIPTION-OF-THE-SLO>",
        "type": "<SLO-TYPE>", // Adhere to the SLOType schema in the API docs
        "description": "<SLO-DESCRIPTION>", // Adhere to the SLODescription schema in the API docs
        "query": "<INFLUXDB-QUERY>" //This query should get back exactly one table with exactly one record. Otherwise, the first table and record will be used for the SLO
    },
    // ...
    {
        "id": "<ID-OF-THE-SLO>",
        "name": "<LONG-NAME-OR-DESCRIPTION-OF-THE-SLO>",
        "type": "<SLO-TYPE>", // Adhere to the SLOType schema in the API docs
        "description": "<SLO-DESCRIPTION>", // Adhere to the SLODescription schema in the API docs
        "query": "<INFLUXDB-QUERY>" //This query should get back exactly one table with exactly one record. Otherwise, the first table and record will be used for the SLO
    }
]
```
